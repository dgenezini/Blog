    • Moving Forgejo from SQLite to PostgreSQL

    The first push after idle took ten seconds; this migration path fixed it without losing history.

    The symptom was a single file lock: first push after an idle night took about ten seconds, and CI plus webhooks stacked behind it. SQLite is a fine default right up to the moment several writers arrive.

    The migration that worked: add a Postgres service to the compose file and point Forgejo at it via env; run forgejo dump for a full backup; extract gitea.db; then clean the SQLite copy for pgloader — drop columns that don’t exist in the Postgres schema and fix NULLs, which is the fiddly part. Start Forgejo against the empty Postgres so it creates the schema, import, verify users, tokens, hooks, and runners.

    Two things I’d check before trusting it: repository timestamps and runner registration. The payoff is boring in the best way — authentication and ref generation stop serializing on one file lock, and the noisy first-push latency disappears.

    Details 

    docker exec -u 1000:1000 forgejo ./forgejo dump -c /data/gitea/conf/app.ini -f /tmp/forgejo-dump.zip
docker cp forgejo:/data/gitea/gitea.db ./gitea.db
cp gitea.db gitea-pgloader.db
sqlite3 gitea-pgloader.db "ALTER TABLE session DROP COLUMN created_unix;"
sqlite3 gitea-pgloader.db "ALTER TABLE hook_task DROP COLUMN repo_id;"
sqlite3 gitea-pgloader.db "UPDATE user SET keep_activity_private=1 WHERE keep_activity_private IS NULL;"

    Env switch on the Forgejo service: GITEA__database__DB_TYPE=postgres, HOST, NAME, USER, PASSWD. Start Forgejo against empty Postgres once so the schema is created, then import.
